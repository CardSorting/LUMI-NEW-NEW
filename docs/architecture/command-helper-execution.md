# Command and helper execution reliability

This audit covers the command transport, action registry, helper delivery, and concurrent file edits. The changes preserve task permissions while removing unnecessary repeated execution and shared mutable helper state.

## Findings and fixes

| Weak point | Root fix | Regression coverage |
| --- | --- | --- |
| Escaped operators reached the shell as `&amp;&amp;` | Normalize escaped shell operators before validation, hooks, display, and execution; preserve quoted strings, comments and heredoc data | Parser/normalizer and command-handler tests, including real shell execution |

## Execution contract

1. Validate and authorize the exact command or assigned tools before dispatch. Transport recovery does not grant additional permissions.
2. Reserve an execution identity before queueing. Do not repeat an active command to learn its status.
3. Attach observers before dispatch. Only a confirmed zero exit code means command success.
4. A foreground timeout releases the caller to do independent work; the underlying command retains ownership and cancellation controls.
5. Use `read_command_output` and `get_execution_state` to reconcile existing work. Retries require corrected intent or explicit idempotency; transport uncertainty is not a retry signal.
6. A helper returns evidence and pending IDs. The parent reconciles them before scheduling overlapping work.
7. File cancellation prevents queued writes from starting and is checked immediately before the filesystem mutation. Once that mutation has been dispatched, a successful commit remains part of the result even if cancellation arrives. Report completed patch steps and reconcile the remainder.

Each helper assignment publishes an `execution_id` before entering the queue. After a cancelled or timed-out batch returns, inspect that ID with `get_execution_state`. An `awaiting_completion` receipt still owns unresolved work. Once it settles, `helper_handoff` contains `files_modified`, `files_viewed`, `pending_command_ids`, and bounded result/error text. Its `truncated` flag explicitly signals omitted evidence. Use `read_command_output` for pending commands; allocating another helper or receipt is not progress by itself.

Command ownership belongs to `CommandRuntime`, keyed by the persisted task ID and task identity. `CommandExecutor` is a task view over that runtime. Replacing or detaching a view prevents its queued launches and controls from taking effect, while the original process keeps its completion observers and cancellation signal. Within the same host, a reopened view reads and controls that same process; disposing the old terminal manager does not discard the retained owner. Only the current view receives status updates. Completed receipts retain plain data, and idle runtime history is bounded to four closed tasks; attached views, queued launches, and live processes are not evicted. Across host restarts, the recovery rules below apply.

The host behavior follows the distinction between shell execution, output, and completion in the [VS Code terminal API](https://code.visualstudio.com/api/references/vscode-api#TerminalShellExecution). The supervised transport waits for process and pipe closure, following [Node's child-process lifecycle](https://nodejs.org/api/child_process.html#event-close). Receipt handling uses caller-supplied intent IDs and equivalent replay results, as described in [AWS's idempotent API guidance](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

File results use the boolean acknowledgment from [VS Code's document save API](https://code.visualstudio.com/api/references/vscode-api#TextDocument). After a successful save, optional editor observations have a one-second wait each; a timeout or rejection skips later editor observations. The write itself is not timed out or replayed. Cleanup waits for the save receipt before releasing mutable editor state. Missing final contents are reported as unavailable, never synthesized from the proposed content or replaced with an empty string.

## Extension-host restart recovery

`ExecutionRecoveryStore` persists records in the extension's global storage under `tasks/<taskId>/execution-recovery`. Its versioned manifest binds the task ID, task ULID, workspace directory, host session and current ownership lease. Separate command, action, helper-batch and tool-call receipts retain stable IDs, input fingerprints, observed states, bounded results and partial handoffs. Command records also retain the command, cwd, historical terminal number, available shell/transport metadata, output and original status-row timestamp. Neither a terminal number nor a PID grants authority.

Admission records are written before command dispatch, action dispatch or a complete mutating tool call. Each record uses a private temporary file, file synchronization and atomic rename. State transitions and settled results update the receipt independently of telemetry, diagnostics and UI delivery. Output observations are sampled at most once per 250 ms while streaming, and captured again on foreground return, explicit reads and completion. Recovery retains the last persisted observation; it never invents output from the interval before a crash.

| Evidence after reopening | Recovered behavior |
| --- | --- |
| An owner is still retained in the current host | Reuse its live process and controls as before |
| A validated persisted command has a confirmed final outcome | Preserve its ID, output, exit evidence and result; expose historical inspection without process controls |
| A persisted command was running, backgrounded, stopping or otherwise unresolved | Report `unknown`, retain correlation and partial output, and expose `recovery.authority: none`; no command or terminal is launched |
| An action was durably queued | Report `not_started`; no closure, scheduling slot, file reservation or queue is reconstructed |
| A helper/action had started but never settled | Report the action as `unconfirmed` and the helper card as `interrupted`; preserve its files, results and pending command IDs |
| A helper had completed, failed or been cancelled | Preserve that recorded outcome and evidence; its old owner cannot regain authority |

Recovery runs once when the task runtime is constructed and makes no process-discovery polls or retries. Repeated recovery and repeated native/batch call IDs inspect or replay receipts. Changed arguments under an existing ID are rejected. Unresolved semantic intents remain fenced while independent new work can proceed. `read_command_output` returns a recovered receipt immediately, including when the caller supplies a wait duration. No stale terminal controls are offered. If the original process has disappeared without a persisted exit observation, its outcome remains unknown; process absence alone does not establish success or cancellation. Intentional repetition after manual reconciliation can proceed in a new task.

Reconciliation updates helper cards by batch ID and command cards by execution ID. A missing helper card is reconstructed once from its durable record at its historical position. A completed action receipt takes precedence over a stale or undelivered progress row. Existing task completion messages retain their position. Legacy command histories with execution IDs are imported without inventing missing cwd or shell metadata; existing output is preserved. Histories that never stored an execution identity cannot acquire one by guessing a terminal number.

Recovered helper owners are retired. File writers check the current lease before preparation, after acquiring ownership and immediately before committing; cancellation checks and save serialization remain in force. Replacing the lease fences old callbacks. An already-dispatched filesystem mutation may still have committed before the crash, so an unsettled write is reconciled from current files and recorded evidence instead of being replayed. UI or tracking failure cannot roll back or redefine that mutation.

Loading validates the manifest, identity, schema version, record filename, lifecycle consistency and size limits. Malformed, foreign, oversized or incompatible records are left untouched and reported through `get_execution_state.recovery`. Valid evidence remains inspectable, while new mutations are blocked pending reconciliation. There is no automatic repair, deletion or retry. Storage is bounded to 1,024 receipts per task and 1 MiB per record; tool-result excerpts over 128,000 characters are explicitly labeled incomplete. Reaching a limit blocks new admission instead of evicting unresolved identities. These are host-restart guarantees, not an exactly-once filesystem transaction or a power-loss guarantee.

The public [VS Code shell execution API](https://code.visualstudio.com/api/references/vscode-api#TerminalShellExecution) supplies execution handles at dispatch/events and requires output reading to begin promptly; it does not provide an API to reconstruct an arbitrary earlier execution handle from a saved terminal ID. VS Code's own [terminal process reconnection](https://code.visualstudio.com/docs/terminal/advanced#_persistent-sessions) can preserve a terminal across reloads, but its presence does not prove which command owns it. The supervised fallback's [child-process pipes and exit listeners](https://nodejs.org/api/child_process.html) belong to the old host and cannot be reconstructed from a PID. This implementation therefore restores durable evidence and reconciliation ownership across restarts, while truthfully declining live attachment for both existing transports. It adds no independent process daemon and never fabricates shell continuity.

## Boundaries

- Durable identities, receipts, partial evidence and duplicate-prevention fences survive host restarts. Live process controls require an actual retained owner; the existing terminal transports cannot reattach their old execution handles after host loss.
- The supervised fallback inherits the extension environment and starts a fresh shell per command. It provides piped I/O rather than a full TTY or persistent interactive shell variables.
- File locks coordinate headless writers in the same extension host. External programs, visual editor saves, and shell commands do not participate in these locks. Comparison detects intervening changes before commit; it cannot provide a filesystem-wide compare-and-swap guarantee.
- A multi-file patch is not an atomic transaction. Completed steps are reported so the parent can reconcile a partial patch without repeating it.
- The real-process tests exercise the local POSIX host. Windows task-tree termination and other IDE implementations still require platform smoke testing.

## Verification

Run `npm run test:execution` with Node 24 LTS. This exercises the backend execution suites and command/helper presentation tests without contacting a model provider. The test configuration resolves TypeScript source imports written with `.js` suffixes. The provider loader uses the same CommonJS module-directory lookup as the shipped extension, so the suite needs no runtime source-rewriting adapter.

Type checks use `tsc --noEmit` and `tsc -b webview-ui`. Build the webview with Vite and the extension with `node esbuild.mjs --production`. These checks do not install or reload the user's running extension.

Verified locally on 2026-09-27 with Node 24.15.0 for restart recovery: **438 backend tests and 60 webview tests passed**. The [restart regression suite](../../src/core/task/__tests__/ExecutionRecovery.test.ts) adds 22 tests covering active and completed task recovery, cancelled helpers, cancelled queued writes, concurrent helpers, malformed/incompatible/foreign state, duplicate recovery, missing processes, legacy histories, and undelivered UI outcomes. Two tests kill a separate Node host running real shell supervision and then load its saved evidence in a fresh runtime. Existing in-process shell reconnection and file-commit tests remain green.

Backend and webview type checks, the extension production build (`node esbuild.mjs --production`), the Vite production build, Biome error checks across 70 changed code/config files, and `git diff --check` passed. The webview build retains existing browser-externalization warnings for `fs/promises` and `path` in `auditBaseline.ts`. No live VS Code restart smoke test, extension installation or publication was performed.
