Subagents let LUMI spawn focused research agents that run in parallel. Each subagent gets its own prompt and context window, explores the codebase independently, and returns a detailed report to the main agent. This keeps the main agent's context clean while gathering broad information fast.

<Tip>
  Subagents is an experimental feature. Behavior may change in future releases.
</Tip>

## How It Works

When LUMI uses the `use_subagents` tool, it launches independent agents simultaneously. Each one:

- Gets its own prompt describing what to investigate
- Runs with a separate context window; configured token and cost limits are shared across the batch
- Can inspect files, make scoped edits, run commands, and use available skills and MCP tools, subject to the task's permissions
- Cannot spawn nested subagents or use tools outside its allowlist
- Returns a result focused on the most relevant file paths for the main agent to read next

Subagent costs (tokens and API spend) are tracked separately per subagent and rolled into the task's total cost. You can see per-subagent stats (tool calls, tokens, cost) in the chat UI as they run.

## Enabling Subagents

Subagents are disabled by default. To turn them on:

1. Open LUMI Settings (click the gear icon in the LUMI panel)
2. Go to **Features**
3. Under the **Agent** section, toggle **Subagents** on

This setting applies in VS Code via extension state (`StateManager`).

## Using Subagents

LUMI does not automatically decide to use subagents. You need to ask for them in your prompt. When the feature is enabled and you mention subagents (or describe a task that benefits from parallel exploration), LUMI will use the `use_subagents` tool.

Example prompts:

- "Use subagents to explore how authentication works and where the database models are defined"
- "Spin up subagents to investigate the API routes, the test setup, and the deployment config"
- "I'm new to this codebase. Use subagents to map out the main entry points, the routing layer, and the data access patterns"

Each subagent prompt should describe a focused research question. LUMI will run them in parallel and synthesize the results.
You can also run only one subagent when the task is small enough that parallel discovery would be unnecessary overhead.

Deep dive: [Working with subagents](/WORKING_WITH_SUBAGENTS) · Code map in [companion brief](/papers/companion-brief.md).

## Auto-Approve Behavior

Subagents follow the **Read project files** auto-approve permission. If you have "Read project files" enabled in [Auto Approve](/features/auto-approve), subagent launches will be auto-approved.

In [YOLO mode](/features/auto-approve#yolo-mode), subagents are always auto-approved.

If auto-approve is off, LUMI will ask for your approval before launching subagents, showing you the prompts it plans to send.

## What Subagents Can Do

The default helper allowlist supports research and scoped implementation. Individual agent configurations may restrict it further:

| Tool | Purpose |
|------|---------|
| `read_file` | Read file contents |
| `list_files` | List directory contents |
| `search_files` | Regex search across files |
| `list_code_definition_names` | List top-level classes, functions, and methods |
| File editing tools | Make scoped changes subject to tool permissions |
| `execute_command` | Run commands subject to the task's command permissions |
| `read_command_output` | Inspect or briefly wait for an existing command by execution ID; included when shell access is allowed |
| `get_execution_state` | Inspect shared commands, queued actions, helper assignments, and recent results without starting work |
| `use_skill` | Load and activate skills |
| Web and MCP tools | Use available search, fetch, and configured MCP capabilities |

Subagents cannot spawn their own subagents. Additional delegation belongs to the parent.

Parent and helper requests receive fresh execution state at provider dispatch, including retries, so they can reuse work already in progress. It includes input previews, attempt limits, queue capacity and wait order, and current approval settings. Missing observation is labeled unavailable rather than implying that nothing is running. Use `get_execution_state` with either a command ID or an action ID to inspect tracked work without starting it again.

Identical assignments are merged within a batch, and duplicate active assignments return the existing execution ID. Batches share the same three helper slots; queued work remains visible and is removed on cancellation. A timeout stops waiting, but does not prove that the underlying work stopped or release a slot still occupied by unresolved work. Runtime permissions and helper tool allowlists continue to apply.

Re-delivery of the same batch call ID joins the existing batch or returns its retained result, without another helper run or another status card. Reusing that ID with different arguments is rejected. Inside a helper, replayed native tool call IDs return the retained tool result rather than repeating a mutation. A new action requires a new call ID; receipts are bounded and scoped to the live task or helper run.

Each helper has its own file editor. Its delegated tools can edit files within the task workspace without opening competing approval prompts; ignore rules, tool allowlists, hooks, and policy checks still apply. Additional authority is reported to the parent as a blocker. Saves compare the current file with the version that the helper read. Conflicts are reported for reconciliation before overwriting another helper's changes. Preparing a headless edit leaves the file untouched, and cancellation never restores stale contents over another writer's work.

Cancellation removes a helper's queued file writes and is checked again before committing a file. If a write has already committed, its result is retained for the parent to reconcile. Cancelling a move after its destination is saved preserves the source and reports the saved destination. Optional editor display, diagnostics and file tracking cannot hold a committed result indefinitely. If the final contents cannot be observed, the result directs the agent to read the file before editing it again.

Helpers finish with an explicit `attempt_completion` handoff: changed paths or findings, verification results, and remaining blockers. Runtime handoffs include any commands still active under the helper's ownership. A response without tools gets one reminder to act or hand off, then returns partial work instead of cycling through repeated prompts. The parent should inspect the handoff and existing command IDs before repeating work.

Every queued assignment has an execution ID. Batch results keep these IDs outside result excerpts so long responses cannot hide them. If a batch stops waiting while a helper is still finishing an edit, its reservations remain held until that operation settles. `get_execution_state` with the helper's ID returns its latest receipt and structured `helper_handoff`, including committed paths and pending command IDs even when the final result arrives after cancellation. Receipt IDs and polling alone do not count as new task progress.

<Note>
  Subagent commands run without interactive terminal input and use the task's existing command permissions.
  Subagents also benefit from command pipelines and filters to narrow output quickly before reading files, for example `rg ... | sort | uniq`.
</Note>

## When to Use Subagents

Subagents work best when you need broad context from multiple areas of a codebase at once:

- **Onboarding to an unfamiliar project**: Ask subagents to map out the architecture, key entry points, and data flow in parallel.
- **Investigating cross-cutting concerns**: Have separate subagents trace authentication, logging, and error handling simultaneously.
- **Pre-edit research**: Before making changes, use subagents to gather context from related files so the main agent can make informed edits without burning through its context window.
- **Large codebases**: When reading many files sequentially would consume too much of the main agent's context, subagents let you explore broadly without that tradeoff.

For small, focused tasks where you already know which files to look at, subagents add unnecessary overhead. Just ask LUMI directly.
