# PB-03 — Automatic Legion formation and specialist capability

## Intent and current status

The user supplies a goal, not a roster or a delegation plan. When the swarm is enabled and the host permits delegation, a delegator observes the task and its evolving context, decides whether a team is useful, forms and operates a bounded team, integrates its results, and continues the sprint. The user should not have to choose roles, create specialists, advance stages, or recover routine failures. Simple or indivisible work can proceed with the parent alone.

**The full design is not yet verified end to end.** `LegionCoordinator` provides classification, formation, lifecycle, and synthesis primitives. Legion is enabled by default, and the first suitable task request connects it to the specialist host under the conditions below. Explicit opt-outs are respected. Real provider and handler integration and restart recovery still require verification. Host instructions, user restrictions, tool availability, security boundaries, and configured budgets always take precedence over automatic delegation.

The earlier in-process executor was removed after deadlocks and state corruption; see the [runtime stabilization report](../../docs/RUNTIME_STABILIZATION_STRATEGY.md). Restoring automatic execution therefore requires a new or demonstrably corrected host runner, not just polling Legion's pending records or restoring the old tool. In particular, a database stream is not an independently running agent, and completion gates must not wait indefinitely on children.

`LegionPipelineRunner.ts` provides the automatic formation decision and stage driver, with in-process duplicate suppression, locked ready-slot claims, prior-stage handoffs, and conservative recovery of ambiguous running work. Task roots are created using a deterministic ID, and a persistent objective token prevents concurrent automatic formation for that root and objective. The runner flushes and reads the claim directly from SQLite before launching a specialist; additional unique tokens prevent multiple drivers for the same formation and duplicate launches of the same specialist attempt. Separate-process tests exercise the tokens on a fresh SQLite database; legacy-root migration remains unverified. In-memory database fallback is rejected for these durability-dependent claims. Tokens are deliberately not expired or automatically stolen: an abandoned formation requires reconciliation. Assignments are serialized. Cancellation does not create a failover replacement. Its classification threshold is a heuristic, not a proof that work is independent. There is no persisted host execution handle; the driver does not impose a timeout on an uncooperative host.

`LegionAgentHost.ts` implements an isolated native-tool provider conversation with bounded turns and reported-token usage, rejects incomplete and unauthorized calls, and requires an explicit handoff. `LegionToolAdapter.ts` constructs independent task and editor state while retaining the parent's approval callbacks, ignore rules, and guard. It exposes command execution and observation through the existing task-owned command runtime. A specialist cannot complete while its commands remain active or unconfirmed; an unresolved command leaves the formation for reconciliation. Command ownership uses the specialist stream ID, allowing the parent to associate tracked unresolved commands with that specialist after recovery. Committed edits update parent revision evidence, and a denied tool stops that specialist. `Task` connects them for the initial act-mode request when native tools are available, no attachments are present, the feature is enabled, and the task merits a team. The parent receives the resulting handoff. Tests cover real file-write and command permission handlers with simulated terminal execution, and the OpenAI-compatible provider against a local streaming endpoint. Other providers, actual terminal integration, and end-to-end restart behavior remain to be audited. A failed host execution is not automatically replayed unless the host explicitly establishes that retry is safe.

`LegionExecutionReceipt.ts` records tool name and bounded paths in SQLite before execution, and marks a returned or uncertain outcome afterwards. Reused operation IDs are rejected. On resume, the parent receives recent metadata, including operations that may have been interrupted; inputs and file contents are not stored in these receipts. A formation intent without a manifest is also reported. This is evidence for parent reconciliation, not proof that a tool completed or that an external operation stopped.

User steering interrupts the active specialist pipeline before the parent sends its next provider request. Tool work already in flight must settle or report an uncertain outcome; a cancelled specialist is not automatically retried.

The host shares a token budget across the specialist team and also applies a cost limit when providers report cost. It deducts recorded prior parent usage before forming a team and persists specialist usage separately on the task's request record; task totals include both while the context-window calculation remains parent-only. Reported usage can arrive late, and providers may omit cost; these limits cannot guarantee an exact billing cap or account for unreported usage. The parent runtime's later requests are not stopped by this specialist budget.

## Runtime contract

1. At task start and meaningful changes in scope, the task owner passes the goal, constraints, relevant context and available capacity to a delegator. It evaluates whether work is separable and beneficial to delegate; record the decision and reasons. Avoid recursive or repeated formations for the same work. If disabled, prohibited, unavailable, or not worthwhile, continue locally and explain material limitations in the final result.
2. The delegator creates a bounded sprint plan: independently actionable assignments, acceptance criteria, dependencies, file ownership, relevant context, expected output, stage, and budget. Select existing archetypes with `classifyTaskForLegion`; roles are internal implementation details, not user inputs. A task-specific specialist is an ephemeral assignment using an allowed archetype and tools, not a new executable role or a registry mutation. Do not give it authority beyond the parent. Persist the plan and formation before dispatch.
3. A pipeline runner dispatches eligible child tasks to the actual host execution mechanism. It must associate each host execution with its formation, slot and attempt, deliver the assignment, and translate real completion, failure, cancellation and timeout into the existing stream lifecycle. Merely creating a pending task is not execution. Respect concurrency limits and stage dependencies; avoid overlapping writes through explicit ownership and serialized integration. Current file reservations are advisory and non-atomic, so they cannot enforce exclusivity.
4. The coordinator receives reports and evidence, checks acceptance criteria and task alignment, integrates results, and updates the rolling roadmap. Advance stages only after dependencies settle. Failed or incomplete work is retried or rerouted within configured bounds; if exhausted, the parent handles remaining work where possible and reports unresolved gaps. Never treat a worker's completion assertion alone as proof of correctness.
5. On restart, reconcile persisted formation and host execution identities before dispatching again. Handle duplicate and late events idempotently; preserve terminal states. Propagate cancellation, release resources, and ensure the parent cannot wait forever. Synthesize an honest final report from actual results and verification, including failures and work not performed.

## Implementation and audit checklist

- Identify the real task entry point, host child-execution API, completion callbacks, and restart/cancellation lifecycle before wiring. Add one orchestration owner rather than a second competing scheduler. Confirm host policies allow child agents; never bypass them.
- Define an explicit decision policy for delegation, reevaluation, maximum depth, concurrency, attempts, elapsed time and cost. Cap task-created roles and input size. Persist decisions and correlation IDs; do not use untrusted task or worker text to expand permissions.
- Wire task entry to the decision and formation path, and wire pending eligible slots to actual child execution. Verify the data passed to child agents includes only necessary context and authorized tools. Make dispatch and recovery safe against crashes between persistence and execution; reconcile ambiguous launches before retrying.
- Enforce dependency ordering and write ownership in the runner or integration process. The present check-then-act reservation mechanism is not a lock. Ensure failure, timeout, cancellation and exhausted capacity unblock the pipeline and preserve useful partial results.
- Verify synthesis against artifacts and tests appropriate to the task. Record role selection, attempts, stage transitions, evidence and unresolved outcomes without exposing unnecessary sensitive context.
- Cover end-to-end behavior with a real or faithful host runner: ordinary goal triggers selection and execution without role input; simple task stays local; disabled or forbidden delegation stays inactive; stages and capacity are respected; failure, timeout, cancellation, restart and duplicate events settle correctly; overlapping writes are controlled; synthesis reflects actual results. Include a regression for a child reported complete despite partial work ([PB-08](PB-08-audit-after-interrupted-work.md)).
- Audit settings and documentation against observed behavior. Do not declare the feature automatic until the task entry, dispatch, lifecycle, recovery and integration paths all pass end-to-end tests.

## Maintainer extension: permanent archetypes

Adding an archetype is a developer maintenance operation, not a step required from the user during a sprint. Prefer an ephemeral task-specific assignment when existing capabilities suffice. When a reusable capability truly needs a permanent role:

1. Add its ID to `LegionSpecialistRole` and `CanonicalLegionSpecialistRole` in `AgentSwarmConfig.ts`; normalize any aliases.
2. Add a `LEGION_SPECIALIST_REGISTRY` entry in `LegionCoordinator.ts` with a unique codename, allowed subagent type, capabilities, layers, execution boundary, weighted keywords and file patterns. Avoid broad keywords; matching uses word prefixes.
3. Ensure `classifyTaskForLegion` and `getStageForExecutionOrder` agree on execution order and stage. Check remediation selection and fallback roles.
4. Update `LEGION_SPECIALIST_ARCHETYPES` in `FeatureSettingsSection.tsx`, and add classification, formation, stage and failure tests. Include unrelated tasks to detect over-selection. Test the autonomous host path as well as the registry primitives.

See [PB-05](PB-05-recover-a-failed-legion-formation.md) for operator diagnosis, not as a required user workflow. Existing deterministic classification and lifecycle decisions are documented in [ADR-0008](../adr/ADR-0008-deterministic-legion-classification.md) and [ADR-0009](../adr/ADR-0009-legion-lifecycle-dag-failover-terminal-states.md); revise those decisions if implementation changes their guarantees.
